# 渐进超负荷算法(含顶组基线)

> 决定每个动作「下一组该用什么重量 × 几次」的算法。
> **核心创新**:基于「上次顶组重量」的递进,而不是上次 working set 平均。
> 比平均递进更精确,因为顶组代表真实极限。

> ⚙️ **实现在 `scripts/fitness_lib.py`,不在本文档里。**
> 本文只讲「为什么这么设计」,所有数值逻辑以代码为准:
> ```python
> from fitness_lib import next_top_set, adjust_in_session, step_kg, round_to_plate
> next_top_set("倒蹬 45°", {"weight": 80, "reps": 11, "rpe": 7})
> # → {'weight': 82.5, 'reps': 11, 'rpe_target': 8, 'note': '上次 RPE 7 轻松,加 2.5kg'}
> ```
> 自检:`python3 scripts/fitness_lib.py --self-test`
> 这么分工是因为本文以前把算法写成伪代码,`is_large_muscle()` 从来没有定义过,
> 每次训练都要现读表格现推算术 —— 下面第 3 节的例子就因此把腿弯举按小肌群算错了。

## 1. 核心概念

### RPE 是什么(先说清楚,因为整套算法都建在它上面)

力量训练的 RPE **不是**「累不累」的主观感受,而是锚定在
**RIR(Reps In Reserve,这一组做完还能再做几次)** 上的:

| RPE | RIR | 含义 |
|---|---|---|
| 10 | 0 | 力竭,一次都做不动了 |
| 9 | 1 | 还能再做 1 次 |
| 8 | 2 | 还能再做 2 次 |
| 7 | 3 | 还能再做 3 次 |
| 6 | 4-5 | |
| 5 | 5+ | |
| ≤4 | — | 只表达用力程度,**不对应 RIR** |

来源:Mike Tuchscherer 2008《Reactive Training Systems Manual》首创,
Zourdos 等 2016 在 NSCA *Strength & Conditioning Journal* 形式化。
部分文献把 8 记作 2-3 RIR、7 记作 3-4 RIR,本 skill 取上表的整数锚点。

**这条定义有两个直接后果**:

1. **RPE 7 不是「轻松」,是「还剩 3 次」** —— 那是实打实的工作组。
   本文早先用「轻松/刚好/吃力」描述档位,丢掉了 RIR 锚点,而 RIR 恰恰是
   让 RPE 可核对的东西(能数的次数 vs 说不清的感觉)。已改。
2. **报数时可以直接报 RIR**。「还能再做 2 个」比「大概 RPE 8 吧」更可靠,
   因为前者是数出来的,后者是估出来的。用 `fitness_lib.rir_of(rpe)` 双向对照。

**半档(7.5 / 8.5 / 9.5)是圈内标准用法**,表达「确定还能做 2 个,也许 3 个」。
用户目前只记整数,代码两种都支持,不需要改记法。

> ⚠️ **准确度的已知局限**:自评 RPE 在**低次数大重量**组上相当准,
> 但在**高次数**组上误差很大 —— MASS Research Review 引的数据是
> 70% 1RM 下训练有素者平均偏差 **5.15 ± 2.92 次**。
> 用户的提踵 ×15、髋内收 ×15、腿屈伸 ×12 都属高次数区间,
> 也就是说驱动递进的 RPE 恰恰在这些动作上最不可靠。
> 算法目前对所有动作一视同仁地信任 RPE,**这是个待决策项**(见 SKILL.md Open Questions)。

---

### 顶组(Top Set)定义
- **组类型 = 顶组**:RPE ≥ 8(≤2 RIR)的最高强度组
- 通常是**每动作最后一组**(或唯一的最重组)
- 例:倒蹬 `80×10×4` → 第 4 组是顶组(80×10 RPE 8)
- 例:RDL `35×8×4` → 全部 RPE ≤ 7 → 第 4 组算「准顶组」按 RPE 7 处理

### Working Set 定义
- **组类型 = 正式**:非热身、非顶组的标准组
- 通常占每动作 50-70% 组数

### 热身 / 收尾
- **热身**:激活神经 + 关节,RPE ≤ 5,重量 < 50% 工作重
- **收尾**:高次数低强度泵感,RPE ≤ 7

## 2. 顶组基线查询(Plan 阶段必做)

### 目的
- 知道「上次这个动作做到多大多重」→ 决定「今天从哪开始」

### 查询

```bash
# 训练组表 ID: <TABLE_ID_TRAINING_SET>(2026-08-01 实测)
lark-cli base +record-list \
  --base-token <YOUR_BASE_TOKEN> \
  --table-id <TABLE_ID_TRAINING_SET> \
  --filter-json '{"logic":"and","conditions":[["动作","==","倒蹬 45°"],["组类型","==","顶组"]]}' \
  --sort-json '[{"field":"日期","desc":true}]' \
  --format json --limit 1
```

⚠️ 参数是 `--filter-json` / `--sort-json`。本文早先写的 `--filter "AND(CurrentValue.…)"`
是**原生 OpenAPI 的写法,lark-cli 不认**,照抄必然失败。

查不到记录 = 首次练此动作 → `next_top_set(action, None)`,它会返回按肌群的
保守起始区间并要求用户确认(而不是像旧实现那样不管什么动作都给 20kg × 12)。

## 3. 递进算法

### 输入
- `action`:动作名
- `last_top`:上次顶组 `{weight, reps, rpe, date}` 或 `None`
- 隐含输入:`is_large_muscle(action)`(决定递进幅度)

### 大肌群 vs 小肌群

| 类型 | 包含肌群 | 默认递进 |
|---|---|---|
| 大肌群 | 胸 / 背 / 股四 / 腘绳 / 臀 | ±2.5 kg |
| 小肌群 | 肩 / 臂 / 小腿 / 核心 | ±1 kg |

动作→肌群的映射表在 `fitness_lib.ACTION_MUSCLE`,判定用 `is_large_muscle(action)`。

⚠️ **注意腘绳属大肌群**:俯卧腿弯举、RDL 都是 **±2.5 kg**。
本文旧版把俯卧腿弯举按 ±1 kg 举例,是错的 —— 它练腘绳,归「腿」。
认不出的动作 `is_large_muscle()` 返回 `None`,`step_kg()` 保守按 1 kg 处理。

---

### 递进规则

`next_top_set(action, last_top)` —— 实现见 `scripts/fitness_lib.py`。

| 上次顶组 RPE | 判定 | 动作 | 新 RPE 目标 |
|---|---|---|---|
| < 7.5 | 轻松 | 加 1 个步长重量,次数不变 | 8 |
| 7.5 ~ 8.5 | 刚好 | 重量不变,加 1 rep | 8 |
| 8.5 ~ 9.5 | 吃力 | 维持 | 8 |
| ≥ 9.5 | 力竭 | 减 1 个步长 + 减 2 reps | 7 |
| 未记录 | — | 维持,并要求用户确认 | 8 |

**为什么用区间而不是判等**:用户实际只记整数 RPE
(截至 2026-08-03 的 98 条记录全是 5/6/7/8/9,无小数)。区间不是为了小数,
而是为了兜住 `==` 判等留下的失控 `else` 分支 —— 旧实现写 `rpe == 8` / `== 9` / `else`,
**else 会吞掉一切非 9 的值**:

- 热身组记的「≤ 5」(真实用过 3 次)→ 落进 else → 判成力竭 → 下组减重
- 打字漏小数点或多按一位(8 打成 88)→ 静默减重,不报错

区间写法让每个值都落进明确的档位,边界靠保守一侧取。**不需要用户改记法。**

**配重片粒度**:算出来的重量要能真加得上。8/02 腿弯举算到 26 kg,但器械没有 1 kg 片,
只能停在 25 kg。用 `round_to_plate(weight, plate=2.5)` 按实际可用片重取整。

## 4. 训练中实时调整

### 异常处理流程
```
用户报数(动作 重量 次数 RPE)
  ↓
校验(重量/次数/RPE 在合理范围)
  ↓
更新 sessions/YYYY-MM-DD.md
  ↓
按 5 项反馈契约返回(详见 SKILL.md)
  ↓
触发调整?(RPE 异常 / 设备被占 / 容量超 2x)
  ↓
是 → 调整下组(±2.5kg / 换动作 / 强制收尾)
  ↓
更新 Plan + session 文件
```

### RPE 异常调整

`adjust_in_session(action, actual_rpe, target_rpe)` —— 实现见 `scripts/fitness_lib.py`。

| 实际 RPE − 目标 RPE | 判定 | 下一组调整 |
|---|---|---|
| ≥ +1 | 偏吃力 | **−1 个步长** |
| −1 ~ 0 | 符合 | 维持 |
| ≤ −1 | 偏轻 | **+1 个步长** |
| ≤ −2 | 明显偏轻(状态好) | **+2 个步长** |

「步长」= 该动作的 `step_kg()`,大肌群 2.5kg / 小肌群 1kg,和第 3 节同一套。

⚠️ **别把这一节和第 3 节搞混,它们决定的是两件事**:

| | 第 3 节 `next_top_set` | 本节 `adjust_in_session` |
|---|---|---|
| 时机 | 训练**前**排计划 | 训练**中**报数后 |
| 跨度 | 跨天(上次顶组 → 今日顶组) | 组间(这一组 → 下一组) |
| 依据 | 上次顶组的 RPE | 刚做完这组的 RPE |

本节旧版写死 ±2.5kg / +5kg(小肌群 +2kg),和第 3 节的大小肌群步长对不上。
现在两处统一走 `step_kg()`,只有一套步长定义。

### 设备被占 → 替换动作
- 查 `exercise-substitutions.md`,选**最接近的替代**
- 反馈模板第 3 项同步更新备选列
- 例:腿屈伸机被占 → 用坐姿推胸(临时加项,等机器期间)

### 单动作容量 > 计划 2 倍 → 强制收尾
- 例:动作 1 计划 3,200 kg,实际到第 3 组已 6,400 kg → 停止,不再加新组
- 防 7/8 力竭重演

## 7. 异常边界

### 算法不适用场景
- **首练**:`next_top_set` 返回 `weight=None` + `needs_confirmation=True`,
  并给出按肌群的建议区间(`FIRST_TIME_HINT`)。**不要自己编一个起始重量** ——
  旧版不管什么动作一律 20kg × 12,对提踵偏轻、对髋外展偏重,基本没法直接用。
- **动作替换**:走 `substitute_weight(原重量, 原动作, 替代动作)`,
  换算系数表在 `fitness_lib.SUBSTITUTIONS`(exercise-substitutions.md 的机器可读版)。
  - 例:杠铃深蹲 → 哈克深蹲,重量 × 0.8;倒蹬 → 哈克深蹲 × 0.7
  - 未收录的组合会明确返回「需人工判断」,不会瞎给系数
- **伤病**:不递进,直接 baseline 维持

### 算法输出需校准
- **用户 override**:任何算法输出,用户明确说"我想试 X" → 直接采用
- **客观异常**:动作中脚踝/关节痛 → 立刻停,算法输出作废

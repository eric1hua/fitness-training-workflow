# 飞书 Base 录入规范与跨 agent 对齐

2026-08-06

## 问题

两台机器上有两个独立实现在往**同一个飞书 Base** 写数据：本仓库的
`fitness-training-workflow`（iMac），和另一台 Mac mini 上的 `fitness-coach`。
两边的记录 ID 约定恰好一致，所以一直没打架——但那是巧合维持的和平，
没有任何共同的录入契约。已经产生的实际后果：

| 现象 | 根因 |
|---|---|
| `容量kg` 整列为空 | 本仓库依据 `base-schema.md` 的记载当成公式字段过滤掉，记载是错的 |
| `开始`/`结束` 12 小时制（2026-08-04）| `fmt_datetime()` 对输入不设防，拿到什么拼什么 |
| `总次数` 缺失（2026-08-02）| 没人规定它必填 |
| `配速` 写成 `11:41 /km` | 没人规定不带单位 |
| 有氧没记坡度 / 阻力 | 没规定记在哪 |
| 组记录挂不到训练日上 | 双向链接只有本仓库维护 |
| 出问题不知道是谁写的 | 没有署名字段 |

前六条是同一个根因：**没有共同契约**。修具体几条脏数据只是治标。

## 被推翻的原始需求

最初的需求是"在 skill 里加一个先拉取 Base 数据到本地的动作"，理由是两个 agent
需要数据同步。核实后不成立：

- 计划阶段（`SKILL.md` 阶段 1 第 1、3 步）本来就**实时查 Base**，不依赖本地缓存
- 训练中是预计算应答表，全程零工具调用，也不碰网

本地缓存对正确性没有贡献，因此不做。真正缺的是录入契约。

另一台机器上其实**已经有** `bitable_pull.py`（飞书→本地，按 `bitable_record_id`
幂等去重），注释明写为多 agent 场景设计。所以那个方向的能力也不缺。

## 方案

**一份规范，两处强制，一处兜底。**

```
data-entry-spec.md  ← 唯一真源
     ├── base_writer.validate_record()   前置校验（A 侧）
     ├── 交给 B 的 prompt                 前置校验（B 侧，自行实现）
     └── base_audit.py                    后置审计（单点，覆盖两侧）
```

### 为什么审计是单点而校验要做两遍

前置校验必须在每个实现里各做一遍，漏一个就白做。审计查的是 **Base 本身**，
在任意一台机器上跑一次就覆盖所有写入方，还顺带抓存量脏数据。

这是整个设计里性价比最高的部分。曾考虑把校验逻辑做成两边共享的库，否决了：
另一台机器在 SMB 网盘那头，跨机器共享 Python 依赖要么断连要么版本漂，
收益不抵风险。规则本身只有十几行，各写一份可接受——**只要规范文档是唯一出处**。

### 关键取舍

**`训练者` 字段废弃而非删除。** 每个训练者已各自一张独立表格，字段没有区分作用。
删字段会连历史值一起没，且 B 的 `map_record()` 还在写它，不同步改会报错。
保留不写，成本最低。

**`录入agent` 是新增的核心字段。** 格式 `<agent>@<主机>`，四张表必填。
没有它，审计报出违规也无法定位是哪个实现写的，只能靠日期猜。

**`--fix` 只修有唯一正确答案的三类**（配速去单位、时间归一、总次数按当日训练组
求和回填）。缺链接、缺 `录入agent`、`容量kg` 为空只报告——那些要么需要判断归属，
要么该由写入方补，自动猜一个填进去比空着更糟。

**时间形状自适应。** `开始`/`结束` 是 DateTime 还是文本字段尚未实测。
与其猜，`base_audit.infer_time_form()` 照着表里已存在且被接受的值的样子回写——
它们是活证据。`validate_record()` 同时接受 `HH:MM` 和完整 datetime 两种形状，
因为它们是同一个东西的两个层次：前者是面向录入方的输入格式，后者是 DateTime
字段的 CellValue。

## 实现要点

### 端到端自检抓出的真缺陷

分开测 `build_*` 和 `validate_record()` 都会绿，但真实链路上 build 的产物要经
`enforce_spec()` 再发出去。补上"构造出来的 payload 必须过得了自己的校验"这条后，
立刻抓出两个问题：

1. `fmt_datetime()` 输出完整 datetime，而校验只认 `HH:MM` —— 真实写入会被自己拦下
2. `build_set_records()` 对 `肌群`/`类别` 静默兜底成空串，而规范要求必填

第 2 个是真 bug 而非测试过严：空 `肌群` 会让递进步长按小肌群算（+1kg 而非 +2.5kg），
部位轮换也判不出练过什么。改为用 `fitness_lib.muscle_of()` 推导，推不出就报错。

顺带在 `fitness_lib` 补了 `category_of()`：`肌群 → 类别`。`臂` 在 `TOPIC_MUSCLES`
里同属推和拉，但类别选项本身就有「肩」「臂」两项，映到自己即可，歧义消失。

### 校验挂在哪

`run_lark_cli()` 是所有写入的唯一入口，从扁平参数里提 `--table-id` 和 `--json`
来校验。**只校验新建**：带 `--record-id` 或 payload 含 `update_records` 的是局部
更新（如回填 link），字段本来就不全，拿整表必填清单去卡只会误报。

dry-run 只警告不退出，保住"零配置也能预览请求体"这条性质。

## 待验证

以下两项以 `lark-cli base +field-list` 实测为准。`base-schema.md` 在 `容量kg` 上
已经错过一次，它记的类型一律不作数：

1. 训练组 `容量kg` 是否公式字段——若是，本次"改为写入"的改动要退回，
   并让 B 去掉这个字段
2. 训练日 `开始`/`结束` 是 DateTime 还是文本——决定 payload 形状。
   面向录入方的输入格式都是 `HH:MM`，不受影响

另需在 Base 侧为四张表新增 `录入agent` 字段（写操作）。

`lark-cli` 在 Claude Code 的 shell 里返回 `not_configured`（token 存 macOS
keychain，非交互 shell 解不开），这三件事需要在 openclaw 环境里执行。

## 验证

```bash
python3 scripts/fitness_lib.py --self-test    # 37 项
python3 scripts/base_writer.py --self-test    # 42 项（原 13）
python3 scripts/base_audit.py  --self-test    # 23 项
```

三个自检都不需要 `config.json`，不碰网络。
